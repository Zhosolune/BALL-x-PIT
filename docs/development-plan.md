# BALL x PIT 局内决策助手 Mod 开发计划

更新时间：2026-10-09。状态：P0、P1 已完成；游戏插件尚未接入。阶段交付见 [P0 规则与场景说明](p0-rules.md) 和 [P1 离线核心](p1-core.md)。

## 1. 目标与完成标准

自动读取当前角色、已持有弹珠、被动、等级及选择界面信息，在后台静默完成分析，为每个候选操作规划可能的发展路线，并给出路线分数、候选分数和推荐标记。

完整交付必须覆盖普通升级、进化、融合及相关选择界面。仅实现三选一弹珠路线预览属于中间阶段，不能作为完整需求完成。

主要交互：

- 用户照常玩游戏，无需手动输入角色、装备或候选项。
- 每个候选项附近显示分数；最推荐的候选项显示文字或图标标记，不能只靠颜色区分。
- 右上角展示候选项的发展路线、每条路线的分数、已有材料、缺失材料和推荐理由。
- 面板默认显示推荐候选的优先路线，悬停或手柄焦点切换到其他候选时同步查看该候选的路线。
- 每个候选默认展示前三条不同路线，可展开查看更多；每条路线保留全部已规划步骤和所需材料。
- 打开、刷新、完成选择、离开界面时自动更新或隐藏；弹珠与被动混合出现时一起比较。
- 分数接近时显示“接近”，默认只标一个首选，并简述取舍；信息不足时显示“信息不足”，不作确定推荐。

首个目标平台为 Windows Steam PC，技术候选为 C#、BepInEx 6 IL2CPP、Harmony、Unity UI。具体运行时与依赖版本在接口验证后锁定。自动选择、修改伤害或掉落、写入游戏存档、云服务、机器学习训练不在当前范围内。

源码证据详见 [可行性调研](mod-feasibility.md)，本计划沿用其中固定的源码版本。

## 3. 数据与逻辑边界

保持一个插件项目，测试使用同一代码库的轻量测试项目；初期不建设独立服务、数据库或通用插件框架。以下是逻辑职责，不要求每个对象单独创建文件。

| 数据 | 最少内容 | 约定 |
| --- | --- | --- |
| 局内快照 | 本局标识、角色 ID、装备实例、等级、界面类别、候选、状态版本 | 从真实游戏读取，不根据上次点击推测装备 |
| 装备实例 | 实例标识、物品 ID、类别、等级、融合组成 | 用实例区分多个材料；未知内容保留未知状态 |
| 候选操作 | 候选标识、画面顺序、操作类别、输入材料、结果 | 新物品、升级、进化、融合分别表达 |
| 规则数据 | 角色标签、物品效果标签、配方、消耗/等级条件、版本和来源 | 游戏 Slug 与外部工具 ID 显式映射 |
| 路线 | 步骤、每步材料、预计升级需求、未满足条件、最终状态 | 不将可选分支的材料合并为同时拥有 |
| 分析结果 | 快照版本、候选分数、各路线分数、理由、信息完整度、首选标识 | 只应用于生成它的局内状态和界面 |

数据优先来源：游戏内部可验证的数据；其次是有明确来源与使用条件的本地规则库。无法确定的角色机制、升级收益、配方条件不填写猜测值。

“球比伦抉择台”可作为数据表达与规则参考：其代码与游戏数据授权范围不同。导入前检查具体许可、保留声明、核对游戏版本；不得默认 game-data.js 属于 MIT。规则库无需一开始覆盖所有角色，但未支持的内容必须在界面中体现；完整发布要求覆盖声明支持版本的角色和可选物品。

## 4. 路线规划

### 4.1 按操作后的局面分析

先为每个候选构造选择后的假设状态，再比较后续发展。

- 获取弹珠或被动：增加对应实例并占用相应槽位。
- 普通升级：应用实际等级变化和已知效果差异；不假定每级收益相同。
- 进化：扣除真实材料实例，加入结果，重新计算协同与槽位。
- 融合：按已核实的规则处理组成、等级、效果与后续配方资格；不得将被消耗的材料继续当作独立持有。
- 非弹珠/被动选项：优先读取实际出现的类别；具备规则时纳入比较，否则标记未评估。存在未评估候选时只能称“已评估项中推荐”。

每个操作需要验证合法性。槽位已满、材料不足、等级不满足等情况不能拿高分掩盖非法状态。

### 4.2 有边界的多步规划

将配方表示为“材料集合 → 结果”，保留替代配方及材料数量。初始规划最多向前展开三次进化或融合操作，每层保留最多二十个不同状态，作为待性能验证的初始预算。

只在游戏规则证实某种融合结果可参与后续配方时，才继续向后展开。未知机制不展开成虚假路线。

规划必须：

- 防止循环，合并重复状态，同时保留具有不同材料成本的替代路线。
- 记录缺失物品与等级差距，将获取材料和升级需求纳入成本。
- 使用后续操作中的真实消耗，避免同一材料被多个步骤重复使用。
- 将终点收益、当前协同、槽位成本和获取负担共同用于排序。
- 将未出现的材料视为条件；没有掉落概率数据时，只用明确的成本折扣，不编造成功概率。
- 标明规划范围，例如“最多前瞻三次操作”；不把有限搜索包装成全部未来路线或全局最优。

阶段、波次等信息只有游戏能可靠读取且能解释其作用时才引入；不能用现实时间简单代替局内进度。角色特殊限制应覆盖通用槽位与机制规则。

## 5. 分数与推荐口径

### 5.1 分数的含义

分数表示当前状态下的规则评估优先级，不表示胜率或完成路线的概率。候选分数用于决定本次操作，路线分数用于说明选择后的发展方向；二者分别标注，不能混用。

评分由以下可解释项组成：

| 项目 | 评价内容 |
| --- | --- |
| 立即收益 | 升级或替换后当前能力的变化 |
| 角色契合 | 与角色触发方式、伤害机制、槽位限制的关系 |
| 组合协同 | 与当前弹珠、被动及融合组成的互补或冲突 |
| 发展潜力 | 可达结果的价值及连续发展空间 |
| 机会成本 | 消耗已有核心、占用槽位、损失其他路线 |
| 获取负担 | 缺失材料、升级次数、路线长度与进度压力 |

先用小规模场景校准这些权重，存入带版本号的内部配置，不提前宣称存在最优固定权重。

### 5.2 候选分数与路线分数

- 候选原始效用 = 选择后的当前状态效用增量 + 有界前瞻的潜力增量 − 本次额外成本。各成本只记一次。
- 路线原始效用 = 该假设路线相对选择后的状态带来的增益 − 材料获取与执行负担。终点当前能力和未来能力不能重复计分。
- 候选潜力采用有限路线中的最佳可行发展方向；没有进化路线的选项仍可凭当前收益取得高分，路线数量本身不加分。
- 若本次是已有球升级，“缺少的升级次数”随之减少，但材料仍按真实状态记录。
- 使用固定的、经场景校准的显示映射输出 0–100 分；不将每轮最高项强制变成 100 分。保留原始效用进行排序，避免取整或截断造成错误并列。
- 尚未支持的关键机制降低信息完整度或停止确定推荐；信息完整度是规则覆盖程度，不是统计置信概率。
- 原始效用接近时按已定义的差值阈值提示“接近”；完全并列采用稳定规则给出默认首选，并明确说明差异不足。

每次分析保留影响最大的两到三条理由，以及主要风险。开发时可检查评分分项，产品面板默认只显示易懂的结论。

## 6. 界面与后台运行

- 候选分数绑定真实候选标识和按钮位置，不能只按数组下标复用旧标记。
- 推荐标记包含“推荐”文字或可识别图标；低信息完整度显示“参考”，不冒充确定结论。
- 路线面板显示“当前可执行 / 材料已齐但等级不足 / 后续规划”等状态，避免混淆。
- 进化、融合界面如采用分步选择，需要展示当前步骤可选操作的推荐，并随已选材料更新；完整组合推荐只能在输入数据足够时显示。
- 原型可用 IMGUI 验证文字显示；正式候选标记和面板优先使用游戏实际 UI 体系，字体和层级在目标版本上决定。
- UI 复用控件，关闭时清理或隐藏。对窄屏、高 DPI、窗口缩放和手柄导航进行验证，不覆盖原有确认、重选、放逐区域。

静默运行流程：主线程读取快照 → 纯数据规划与评分 → 检查局内及界面版本 → 主线程更新 UI。

初期先测有界计算的耗时，只有确有需要才使用后台工作线程。后台线程不得访问 Unity/IL2CPP 对象。候选重选、读档、结束本局或关闭界面后，旧结果必须作废；主线程应用结果前再次核对版本。

数据或接口异常时撤除错误标记，记录限频日志，保留原生选择流程。用户无需弹窗或手动维护状态。初期不保存局内历史，仅提供关闭显示、面板缩放和开发日志等必要配置。

## 7. 开发阶段

P0、P1 已完成，其余阶段尚未开始。P0–P1 不依赖本地游戏；P2 以后需要目标版本类型资料和真实测试环境，该环境可由用户或其他测试者提供。

| 阶段 | 工作 | 交付物 | 通过条件 |
| --- | --- | --- | --- |
| P0：规则准备 | 确认数据来源、版本与授权；定义快照、操作、配方及评分口径 | 小规模规则样本、场景清单、类型设计 | 来源可追溯；未知规则有标记；弹珠和被动可同时表达 |
| P1：离线决策核心 | 实现合法操作模拟、路线规划、分项评分、理由与首选 | 不引用 Unity 的核心和自动化测试 | 通过消费、替代材料、等级、角色限制和混合候选场景；重复输入结果一致 |
| P2：游戏接口验证 | 锁定游戏与加载器版本；读取角色、装备、等级、全部候选；检查各界面生命周期及配方入口 | 只读接口原型、接口清单、现场核对记录 | 不靠悬停即可读到全部候选；刷新/读档/换局正确；主要类型和操作匹配真实画面 |
| P3：普通升级推荐 | 接入实际规则与 ID 映射；显示弹珠/被动/升级分数、首选标记和路线面板 | 可运行的首个内部版本 | 自动读取，无用户录入；混合候选共同排名；打开/重选/关闭正确；中文与鼠标/手柄验证 |
| P4：进化与融合 | 接入两类真实操作，支持材料消耗、组合效果、槽位变化和分步选择 | 多界面内部版本 | 三类界面均给出推荐；与实际操作后状态一致；融合组成不遗漏、不重复计入材料 |
| P5：策略校准与性能 | 扩展声明支持的角色和物品；校准权重；控制搜索预算和过期任务 | 版本化规则库、场景结果、性能记录 | 支持内容有覆盖清单；明显错误推荐已处理；满足目标性能和显示检查 |
| P6：发布验证 | 在指定游戏版本验证安装、禁用、更新与移除；整理已知限制 | 插件包、中文说明、兼容版本与测试报告 | 干净环境可运行；完整需求通过验收；发布包不附带游戏本体或 interop 程序集 |

P2 是关键检查点：无法准确读取候选或角色时，先解决适配问题，不能以手动录入替代核心需求。无法可靠取得某项特殊机制时，缩小声明支持的范围并显示未评估；不将部分支持标记为全功能发布。

## 8. 验收矩阵

### 算法正确性

- 相同物品在不同角色或不同被动组合下，因明确规则产生可解释的差异。
- 同时比较新弹珠、新被动、已有物品升级；强即时收益可以胜过长进化链。
- 具备替代材料、多材料、重复材料、循环和无路线的测试场景。
- 材料已持有但等级不足时，不显示“当前可进化”；升级后差距正确减少。
- 满槽、特殊角色槽位、融合球及材料消耗得到正确处理。
- 不同操作顺序、相同终点与不同成本的路线不会被错误合并。
- 数据缺失时不输出确定首选；评分分项与文字理由保持一致。
- 未知未来材料不当作已拥有；没有实测数据时不输出概率。

### 游戏运行与 UI

- 覆盖首次选择、重选、放逐、连续升级、进化、融合、暂停恢复、读档和结束本局。
- 覆盖弹珠/被动混选、候选数量变化、自动选择角色及手柄导航。
- 用截图或日志与实际画面对照验证所有候选、等级、角色和操作结果。
- 刷新时不会把旧推荐写到新按钮；关闭后不会闪回面板，换局不残留装备状态。
- 原生鼠标、键盘、手柄选择、确认和退出行为正常；分析失败不会阻止选择。
- 至少检查 1280×720、1920×1080，以及 125%/150% 显示缩放下的窗口布局。中文、分数和标记不裁切；面板不遮挡关键控件。

### 性能与推荐质量

- 初始目标：快照读取和 UI 应用分别尽量控制在 2 ms 内；有界核心计算 p95 ≤ 50 ms；界面就绪至推荐可见 p95 ≤ 150 ms。均为待目标机器验证的预算，不是已达成结果。
- 在普通、长链和融合复杂状态中分别采样至少三十次，记录机器、游戏版本、规则版本、耗时及搜索节点；必要时调整预算与展示范围。
- 不每帧搜索，不无限递归；反复打开/刷新至少五十次后，没有持续增长的面板对象或任务积压。
- 首轮建立不少于二十个有明确预期或取舍说明的场景，覆盖不同角色、槽位压力、被动协同和长短期矛盾；实际对局复核明显异常。
- 不以少量胜负记录证明胜率提升。推荐质量先以规则一致、理由可信和明显错误减少来验收。

## 9. 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 游戏更新改变接口 | 固定支持版本，启动时检查必要类型；失败时关闭对应推荐并记录原因 |
| 外部规则不完整或译名不一致 | 使用内部 ID 映射、版本和来源；以目标游戏核对结果为准 |
| 长路线被过度高估 | 限制搜索深度，扣除材料与升级负担，保留即时收益比较 |
| 融合规则判断错误 | P2/P4 单独实测，未经验证的融合组成不用于确定规划 |
| 分数过于主观 | 展示理由、版本化权重、固定场景回归；避免胜率含义 |
| 面板遮挡或中文缺字 | 优先复用游戏字体，支持折叠与缩放，检查窄屏和输入焦点 |
| 异步结果过期 | 快照带局内和界面版本，过期任务取消或丢弃，主线程核对 |
| 与其他 UI Mod 冲突 | 独立标记与层级、幂等创建；优先做干净环境验证，再测试实际使用组合 |

目前不承诺固定工期：P0/P1 的工作可独立推进，P2 的接口和融合机制验证会决定后续适配成本。阶段完成后记录真实进度、耗时与阻塞，不用估计代替验证结果。
